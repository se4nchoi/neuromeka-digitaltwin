## 1. Project intent

This is a browser-based Indy7 palletizing-cell digital twin and operator interface. It combines:

- FastAPI/WebSocket backend telemetry
- Three.js procedural 3D robot and workcell
- Simulation and optional Neuromeka hardware modes
- Palletize and LIFO put-back programs
- Home/zero/jog/direct-teaching controls
- Waypoint acquisition and sequence execution

The longer-term portfolio goal is to demonstrate industrial robotics integration, operator-centered HMI design, telemetry/logging, and explainable diagnostics—not merely a moving 3D demo.

This affects simulation only; hardware `MoveL` behavior remains unchanged.

## 4. Starting on another computer

Prerequisites:

- Git
- Python 3.12+
- `uv`
- A modern browser

```powershell
git clone https://github.com/se4nchoi/neuromeka-digitaltwin.git
cd neuromeka-digitaltwin
uv sync
uv run python run_digitaltwin.py
```

Open `http://localhost:8088`.

If hardware at `192.168.3.7` is unavailable, use Simulation mode. The optional Neuromeka SDK is imported defensively; the simulator works without it.

After pulling Python/backend changes, stop the old process with `Ctrl+C` and launch it again. A browser refresh alone is insufficient.

## 5. Architecture map

| Area | File | Responsibility |
|---|---|---|
| Launcher | `run_digitaltwin.py` | Starts Uvicorn/FastAPI on the configured port |
| API/WebSocket | `src/digitaltwin/server.py` | Commands, REST endpoints, and 30 Hz telemetry broadcast |
| Robot/program engine | `src/digitaltwin/palletizer_engine.py` | Simulation state, hardware calls, programs, I/O, waypoints |
| Kinematics | `src/digitaltwin/kinematics.py` | Craig MDH FK, interpolation, calibrated joint targets |
| Cell configuration | `src/digitaltwin/config.py` | Poses, grid dimensions, speeds, I/O addresses |
| 3D/UI behavior | `src/digitaltwin/static/digitaltwin.js` | Three.js scene, telemetry consumption, controls |
| Interface markup | `src/digitaltwin/static/index.html` | Operator dashboard structure |
| Interface styling | `src/digitaltwin/static/style.css` | HMI layout and responsive styling |

Telemetry flow:

```text
PalletizerEngine state (q, p, I/O, cycle)
    -> FastAPI /ws/telemetry at ~30 Hz
    -> browser handleTelemetry()
    -> targetQ
    -> 60 FPS interpolation
    -> Craig MDH robot transforms
```

## 6. Known limitations and technical debt

1. **No general inverse kinematics yet.** Programmed palletizer poses animate using calibrated joint targets. Arbitrary Cartesian task jogging can still change `p` without producing a physically corresponding `q` pose.
2. **The simulated `MoveL` is a visual approximation.** TCP coordinates interpolate linearly while joints interpolate between calibrated endpoints. It is not yet a solved Cartesian path sampled through IK.
3. **Robot and gripper geometry are procedural approximations.** The view does not yet use official Indy7 URDF/CAD meshes, and the gripper is effectively hardcoded.
4. **No tool registry/tool-frame model.** The backend should eventually expose tool ID, TCP transform, payload, geometry asset, and I/O mapping so the frontend can render the attached end effector correctly.
5. **No collision model.** The arm can visually intersect the table, feeder, pallet, or itself. There is no swept-volume or clearance validation.
6. **No persistent event log or replay.** Current telemetry is transient.
7. **No automated test suite committed yet.** Verification used direct runtime assertions during development.
8. Review the approach-vector math in `PalletizerEngine.get_approach_pose`; its `zy` expression differs from the helper in `kinematics.py`. The current near-90-degree wrist configuration makes the difference small, but the formulas should be unified.

## 7. Recommended next stages

Work in small, demonstrable stages.

### Stage A — Trustworthy telemetry and event logging

- Introduce structured events: timestamp, severity, source, program, phase, target, actual pose, result, and fault code.
- Persist cycle summaries and events to SQLite.
- Add an operator event timeline with filtering and export.
- Add deterministic session replay before adding an LLM.

This is the strongest immediate portfolio addition because it demonstrates observability, traceability, and production thinking.

### Stage B — Tool and asset model

Define an API object similar to:

```json
{
  "tool_id": "parallel_gripper_01",
  "name": "Pneumatic parallel gripper",
  "tcp": [0, 0, 145, 0, 0, 0],
  "payload_kg": 1.2,
  "geometry_url": "/static/assets/tools/parallel_gripper.glb",
  "io": { "open": 0, "close": 1 }
}
```

Store it in backend state, include it in telemetry, and load the matching GLB in Three.js. Treat tool identity and TCP calibration as operational data rather than UI decoration.

### Stage C — Robot model fidelity and collision awareness

- Obtain a licensed/redistributable Indy7 URDF or mesh set.
- Load the actual link meshes and named tool attachment frame.
- Add joint limits and basic collision/clearance warnings.
- Visually distinguish commanded, simulated, and measured paths.

### Stage D — IK and motion validity

- Add numerical IK with joint-limit and continuity constraints.
- Sample Cartesian `MoveL` paths and solve each sample.
- Reject unreachable targets and surface a useful diagnostic.
- Add tests comparing FK(IK(target)) against target tolerances.

### Stage E — Natural-language diagnostics

Only after structured logging is reliable, add an LLM as an explanation layer:

- “Why did the cycle stop?”
- “Summarize the last palletizing run.”
- “Which step had the largest pose error?”

The LLM should read selected structured records and cite event IDs. It should not directly control motion or invent diagnoses from raw prose.

## 8. Portfolio framing

A compelling demonstration should show a complete engineering story:

1. Execute a palletizing cycle.
2. Show commanded versus actual state in real time.
3. Trigger or simulate a controlled fault.
4. Show the event timeline explaining where and why it stopped.
5. Recover safely and replay/compare the cycle.
6. Switch tools and show the correct TCP/mesh/configuration.

That communicates robotics integration, frontend visualization, backend systems design, safety awareness, and operational usability to a possible employer.
